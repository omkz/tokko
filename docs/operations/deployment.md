# Deployment

This document covers first-time production deployment concerns for a
self-hosted Tokko instance on [Kamal](https://kamal-deploy.org): PostgreSQL
provisioning, healthchecks, mail configuration, and a post-deploy
verification checklist. It's a companion to
[`docs/operations/backup-and-restore.md`](backup-and-restore.md), which
covers disaster recovery rather than initial setup.

## Healthcheck

Tokko exposes Rails' built-in `/up` endpoint (`rails/health#show`) as its
deployment healthcheck. It requires no authentication and returns `200` as
long as the app has booted successfully — it does not check the database,
Stripe, SMTP, or any other dependency.

`config/deploy.yml` points Kamal's proxy at it explicitly:

```yaml
proxy:
  healthcheck:
    path: /up
    interval: 3
    timeout: 3
```

Keep this distinction in mind:

```text
/up                    = process/app liveness (is the container up at all?)
deployment verification = dependencies/business functionality (see checklist below)
```

`/up` intentionally does **not** grow into a dependency-readiness probe. A
Stripe outage or a slow SMTP server should not make Kamal think the app
container itself is unhealthy and start cycling it.

## PostgreSQL provisioning

Production uses four PostgreSQL databases on the same server/role:

```text
tokko_production          # primary/business data
tokko_production_cache    # Solid Cache
tokko_production_queue    # Solid Queue
tokko_production_cable    # Solid Cable
```

`config/database.yml` connects to all four using the same connection
settings — `DB_HOST`, `DB_PORT` (default `5432`), `DB_USERNAME` (default
`tokko`), and `TOKKO_DATABASE_PASSWORD` — since the cache/queue/cable entries
inherit the primary's connection config and just point at different database
names.

The Docker image's entrypoint runs:

```bash
bin/rails db:prepare
```

on boot, which creates any of the four databases that don't exist yet and
loads/migrates their schema. Before your first deployment, you have two
options:

1. **Manually provision** all four databases (and the `tokko` role) ahead of
   time, and grant that role ordinary DML/DDL rights on them (`CREATE`,
   `ALTER`, etc., scoped to those databases) — no more than `db:prepare`
   actually needs, or
2. **Grant the connecting role `CREATEDB`** so `db:prepare` can create the
   four databases itself on first boot.

Either is fine. What to avoid: giving the long-lived production database
role broader privileges than necessary (e.g. PostgreSQL superuser) purely
for the convenience of skipping manual provisioning — scope it to what
`db:prepare` and normal application queries actually require.

## Mail configuration

Mailer host/protocol, the default "from" address, and outgoing SMTP are all
driven by environment variables rather than Rails encrypted credentials —
credentials require `RAILS_MASTER_KEY`, which Docker asset precompilation
intentionally runs without.

| Variable | Default | Purpose |
|---|---|---|
| `APP_HOST` | `example.com` | Host used in links generated by mailer templates |
| `APP_PROTOCOL` | `https` | Protocol used in those links |
| `MAIL_FROM` | `no-reply@example.com` | Default "from" address |
| `SMTP_ADDRESS` | `localhost` | Outgoing SMTP server |
| `SMTP_PORT` | `587` | SMTP port |
| `SMTP_DOMAIN` | falls back to `APP_HOST` | HELO/EHLO domain |
| `SMTP_USERNAME` | unset | SMTP auth username, if required |
| `SMTP_PASSWORD` | unset | SMTP auth password, if required |
| `SMTP_AUTHENTICATION` | `plain` | SMTP auth method |

All of these are placeholders in `config/deploy.yml` — set real values for
your domain and mail provider before deploying. `SMTP_USERNAME`/
`SMTP_PASSWORD` are only needed (and only listed under `env.secret`) if your
SMTP provider actually requires authentication; leave them unset for an
unauthenticated relay.

Stripe credentials are unaffected by this and remain in Rails encrypted
credentials (`bin/rails credentials:edit`) — see the README's Configuration
section.

## SSL

Kamal's proxy can terminate SSL for you on a single-server deployment:

```yaml
proxy:
  ssl: true
  host: shop.example.com
```

Replace `shop.example.com` with your real domain — it's a placeholder, not a
required value. If you're behind Cloudflare, set its SSL/TLS mode to "Full"
so the CF-to-app leg is also encrypted. Don't use Kamal's built-in SSL
proxying across multiple web servers — terminate SSL at a load balancer
instead in that case.

## First deploy

Before running `bin/kamal setup`, configure the PostgreSQL connection for the
production primary (and the cache/queue/cable databases, which inherit it) —
see [PostgreSQL provisioning](#postgresql-provisioning) above:

* `DB_HOST` — hostname/IP of your PostgreSQL server, in `config/deploy.yml`'s
  `env.clear` (leave unset only if the app container actually has access to a
  local PostgreSQL Unix socket — not the normal case for a container
  deployment)
* `DB_PORT` — defaults to `5432`, also in `env.clear`
* `DB_USERNAME` — defaults to `tokko`, also in `env.clear`
* `TOKKO_DATABASE_PASSWORD` — a secret, exported in your shell (or provided
  by your secret manager) before running Kamal commands, per `.kamal/secrets`

Exporting `TOKKO_DATABASE_PASSWORD` alone is not sufficient for a normal
containerized deployment — without `DB_HOST` pointed at a reachable
PostgreSQL server, the container has no way to reach the database.

```bash
export TOKKO_DATABASE_PASSWORD='...'

bin/kamal config   # sanity-check the resolved configuration locally first
bin/kamal setup
```

And for subsequent deploys:

```bash
bin/kamal deploy
```

See the README's Deployment section for the full flow, including secrets.

## First owner

Tokko intentionally creates **no default production administrator** and **no
known production password**. `db/seeds.rb` only loads demo data (including
the `admin@tokko.com` account) in `development` — production seeding creates
no users at all.

Once the application is deployed and its database is ready, explicitly
bootstrap the first owner account:

```bash
export TOKKO_OWNER_EMAIL='owner@example.com'
export TOKKO_OWNER_PASSWORD='use-a-long-random-password'
```

These are one-time bootstrap values, not ongoing configuration — don't add
them to `config/deploy.yml` or `.kamal/secrets`.

`bin/rails tokko:bootstrap_owner` needs those two variables present *inside*
the running app container. Passing them with `bin/kamal app exec -e
TOKKO_OWNER_PASSWORD:...` would put the password on your local command line,
where it can land in shell history and briefly show up in local process
listings — avoid that. Instead, use the interactive container shell Kamal
already gives you (the `shell` alias in `config/deploy.yml`):

```bash
bin/kamal shell   # app exec --interactive --reuse "bash"
```

Then, inside that container shell:

```bash
export TOKKO_OWNER_EMAIL='owner@example.com'
export TOKKO_OWNER_PASSWORD='use-a-long-random-password'
bin/rails tokko:bootstrap_owner
unset TOKKO_OWNER_EMAIL
unset TOKKO_OWNER_PASSWORD
exit
```

(If your shell has `HISTCONTROL=ignorespace` set, as many do by default,
prefix each `export` with a leading space to keep the password out of the
container's own shell history too.)

`tokko:bootstrap_owner` requires both variables (aborting with no changes if
either is missing), rejects a password under 12 characters, refuses to
create a second owner under a different email once one exists, and never
prints the password. It's safe to rerun for the same email — e.g. to rotate
the password later.

## Single-server worker design

The example `config/deploy.yml` runs Solid Queue inside the same Puma
process as the web server (`SOLID_QUEUE_IN_PUMA: true`), which is fine for a
single-server deployment. Once you scale to multiple servers, move worker
processing to a dedicated `job` role (see the commented-out `job:` block
under `servers:` in `config/deploy.yml`) rather than running workers on
every web server.

## Post-deploy verification checklist

`/up` returning `200` only proves the process booted — it's not a substitute
for checking that the deployment is actually working end to end. After
deploying, verify:

- [ ] `GET /up` returns `200`
- [ ] the storefront loads
- [ ] dashboard login works
- [ ] the PostgreSQL primary is reachable (dashboard/storefront pages that
      query the database load without error)
- [ ] product image upload works (exercises Active Storage end to end)
- [ ] the Solid Queue worker is running and picking up jobs
- [ ] recurring Stripe recovery tasks (e.g. `RecoverStaleCheckoutsJob`) are
      scheduled and running
- [ ] an outbound email test succeeds
- [ ] the Stripe webhook endpoint is configured in the Stripe dashboard and
      pointed at this deployment
- [ ] logs show no boot or migration failures

This checklist is deliberately manual/operational — it is not something
`/up` performs automatically.
